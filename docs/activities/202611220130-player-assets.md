# Atividade: assets dos jogadores — variações, geração, upload e estilo (PLAN-PLAYER-ASSETS fases 2–5)

**Data**: 22/11/2026 · **Plano**: [Atividade de catálogo de modelos](202611232303-catalogo-de-modelos-do-mundo.md)
(fase 1 concluída no commit `94a2231`; aqui as fases 2–5)

## Investigação

- `game.assets` já era do cache OPFS (assets.js) → o módulo novo é `game.glb`.
- Ponte JS→C# era só notificações (GameInterop) → variação paramétrica precisou de um
  `DotNetObjectReference` extra (`ModelsInterop`) passado como 3º argumento de `game.init`.
- `GLTFFileLoader.importMeshAsync` espera `{json, bin}` pré-parseado (o core SceneLoader
  decodifica o GLB); caminho direto para bytes crus: `SceneLoader.ImportMeshAsync('', blobUrl, '', scene, undefined, '.glb')`.
- O npm `babylonjs@9` não traz mais o bundle UMD dos loaders — o arquivo versionado
  existe em `cdn.babylonjs.com/v{versão}/loaders/...`; optamos por vendorizar no repo
  (pinado, SRI, auditável no git).
- Backend: roteador manual em `app/Api.cs` (MaxBody 64 KB p/ JSON) — upload binário de
  2 MB precisou de leitura própria na rota; `GameWorld.Session` era privado →
  `HasSession`/`SessionName` públicos para autenticar/creditar assets.
- Poly Pizza expõe GLB por modelo com autor+licença na página (Quaternius tudo CC0);
  itch.io/Kenney bloqueiam curl.

## Alterações

- **Fase 2 (variação paramétrica)**: `ModelLoader` guarda instâncias `IModel` e expõe
  `Rebuild(id, seed, detail)`; `src/Models/ModelsInterop.cs` (JSInvokable `VaryModel`);
  `game.models.vary` (descarta protótipos/instâncias com `disposeModel`, re-registra e
  re-espalha na fila de 4 ms/frame); `game.init(canvas, bridge, modelsRef)`.
- **Fase 3 (geração via API)**: `app/WorldAssets.cs` — catálogo persistido em
  `ULTIMA_DATA_DIR/assets/` (gravação atômica), `GlbProcedural` (escritor glTF 2.0
  binário na mão: cristal/totem/flor determinísticos por prompt+seed, mesh não indexado
  com flat normals), adapter Meshy (`MESHY_API_KEY` → job + poll), rotas
  `GET /v1/assets`, `POST /v1/assets/generate`, `GET /v1/assets/jobs/{id}`,
  `GET /v1/assets/file/{nome}` (imutável por sha no nome).
- **Fase 4 (upload dos jogadores)**: `POST /v1/assets/upload` com validação server-side
  (magic GLB, ≤2 MB, ≤30 mil tris via parse do chunk JSON, slug, autor, ≤200 assets);
  cliente `js/workshop.js` (sync do catálogo 30 s, `game.glb.fetchVerified` com
  `baseUrl`, espalhamento determinístico `game.glb.scatter` — RNG mulberry32 semeado
  pelo hash do id: mundo igual para todos); `game.live` expõe `call`/`api`/`token`.
- **Fase 5 (estilo do mundo)**: `game.scenery` (`procedural`↔`lowpoly`, localStorage),
  alternativas CC0 `flora.pine`/`rock.boulder2`/`scenery.grass2` em `glbAltPlacements`
  com as mesmas contagens/regras dos procedurais; no estilo padrão carregam sem
  espalhar. Painel **Oficina do mundo** no HUD (variações, prompt, upload, estilo) em
  `Index.razor` + `extras.css` + `OnWorkshopStatus` no GameInterop.

## Validação

- Backend (curl, dados em tmp): `generate` "cristal encantado azul" → GLB 70 tris,
  base no chão (bbox y∈[0, 0.88]), sha no catálogo; upload válido aceito (mushroom,
  138 tris, creditado); lixo recusado; sem token → 401.
- Navegador (Chrome headless via CDP, cliente servido + backend local):
  - `game.models.vary('tree.pine', {seed, detail:1.5})` → `true`, duas entradas de
    timing sem erro (rebuild + re-espalhamento);
  - `game.workshop.generate('totem de pedra verde')` → "✓ criado e plantado no mundo!",
    3 instâncias determinísticas;
  - sync trouxe os assets criados/upados via curl para o cliente automaticamente;
  - upload pela UI (DOM.setFileInputFiles) publicou "prop.stump" (232 tris) e plantou;
  - estilo `lowpoly` (reload com localStorage): flora.pine 64, rock.boulder2 26,
    scenery.grass2 420 — mesmas contagens dos procedurais, sem placeholders/flutuação
    (inspeção visual por screenshot); DLLs seguem carregadas (personagens).

## Adendo — porte para o motor worker (mesma data)

A frente worker (commit `07ff4f2`) moveu o motor para `game-core.js` rodando em Web
Worker; as fases 2–5 foram portadas na sequência (commit `e4e7054`):

- `models.vary` cruza contextos: core → `host.varyModel` → worker→shell
  (`varyModel`/`varyResult` por request id) → `ModelsInterop` no .NET → descritor
  JSON de volta ao core, que troca e re-espalha;
- o estilo do cenário vem do host no boot (localStorage mora na página);
- `glb.register` devolve `true` (pela ponte só viajam valores JSON — o protótipo
  Babylon é circular e interno);
- o workshop busca os bytes do servidor na main thread (crypto.subtle) e entrega ao
  core por clone estruturado.

Validação no modo worker (Chrome headless via CDP, perfil limpo): 14 assets (6 locais
+ 3 alternativos + 5 do servidor), vary True, generate planta, lowpoly 64/26/420,
0 erros de console, p99 14,7 ms e 0 frames >33 ms. Produção (`e4e7054`): worker ativo,
9/9 assets locais com 450 instâncias, vary funcionando, p99 10 ms; a oficina degrada
com mensagem clara enquanto o backend publicado não ganha as rotas `/v1/assets`.
  - 0 erros de console nas sessões completas.
