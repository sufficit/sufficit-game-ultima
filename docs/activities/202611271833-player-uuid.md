# Persistent player UUID

## Investigation

Network peer IDs routed individual connections and did not provide a stable
player identifier for conversation ownership or telemetry correlation.

## Changes

- The browser generates a UUID v4 from browser cryptography and stores it
  per browser profile. Game sessions and Genius NPC conversation keys use
  that value across room and connection changes. Old Genius snapshots keyed
  by the known short player ID can seed the UUID-keyed conversation.
- Game sessions expose the UUID in their authenticated state. Session tokens,
  character profile keys, and network peer IDs keep their current roles.
  Legacy API clients that omit the UUID receive one derived from their profile
  key. A client that supplies its own UUID resends it on new sessions.
- New Guardian quality events, diagnostics, and legacy dialogue analytics
  events carry the UUID. Older telemetry remains valid and unattributed.
  The public Guardian summary exposes distinct player counts and the number
  of attributed events, while individual UUIDs are retained only by the
  collectors. The UUID is an attribution key, independent of authentication.

## Validation and delivery

- Release publish, RulesSmoke, all 16 JavaScript tests, and all seven
  server integration scenarios passed.
- Chromium passed conversation and garden scenarios on both rendering paths.
  The tests checked migration, stable identity across a room and peer change,
  and matching UUIDs in diagnostics and retried telemetry. Browser Services
  also passed the legacy queue, live session and WebRTC invite checks.
